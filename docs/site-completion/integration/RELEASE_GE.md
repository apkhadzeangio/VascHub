# გაშვების და დაბრუნების პროცედურა

ეს არის მომზადებული ინსტრუქცია. main-ში merge და Production deploy ამ დავალებაში
არ შესრულებულა და ამ დოკუმენტით ავტომატურად არ იწყება.

## გაშვებამდე

1. დააფიქსირეთ ინტეგრაციის PR-ის საბოლოო SHA და დარწმუნდით, რომ ორივე წყარო SHA
   (`715f187…`, `1f314ed…`) მის ისტორიაშია. წყარო PR-ები ცალ-ცალკე არ გააერთიანოთ.
2. ბოლო head-ზე გადაამოწმეთ Checks: PG16 migrations, typecheck/lint, integration,
   build, browser, Docker startup/restart და მედიის persistence.
3. განიხილეთ accepted screenshots და ღია შეზღუდვები. ამ შემსრულებლის 403-იანი
   Production probes წარმატებულ მიღებად არ ჩათვალოთ; ხელმისაწვდომ გარემოში საჭიროა
   უშუალო read-only შემოწმება. SMTP/provider-ის გარეშე reset წერილები არ იმუშავებს.
4. არსებული Railway service-ის metadata-დან ჩაინიშნეთ წინა LIVE deployment ID და
   source commit. არ წაიკითხოთ/გამოაქვეყნოთ secrets და არ შეცვალოთ variables, დომენი
   ან მონაცემთა საცავი. შემოთავაზებული ცვლილება სქემასა და მიგრაციებს არ ცვლის.

## დამტკიცების შემდეგ

1. გააერთიანეთ მხოლოდ შემოწმებული ინტეგრაციის PR მიმდინარე main-ში, PR head SHA-ის
   შემოწმებით. მანამდე main-ის ახალი ცვლილებების არსებობისას განაახლეთ ინტეგრაცია
   და შესაბამისი შემოწმება; სხვისი კომიტები არ გადააწეროთ.
2. გამოიყენეთ არსებული Railway deploy ინტეგრაცია. დაადასტურეთ, რომ ახალი LIVE
   deployment-ის source commit რეალურად დამტკიცებულ merge-ს ემთხვევა.
3. შეამოწმეთ Production-ის `/`, `/posts`, `/search`, `/library`, მოქმედი საჯარო
   რესურსი და login გვერდი. შეამოწმეთ desktop/mobile მენიუ და კონსოლის შეცდომები.
4. რეალური სტატიები სატესტოდ არ შექმნათ/გამოაქვეყნოთ. ექვსი არსებული Draft უნდა
   დარჩეს Draft-ად და Clinical Library-ის რეალური ჩანაწერები — უცვლელი.

## კოდის წინა ვერსიაზე დაბრუნება

1. შეცდომიანი გაშვებისას ჩაინიშნეთ მისი deployment ID/source SHA და ლოგები.
2. არსებული Railway service დააბრუნეთ წინასწარ ჩანიშნულ წინა LIVE deployment/source
   commit-ზე. არ წაშალოთ სერვისი, volume, PostgreSQL ან Media.
3. შეამოწმეთ ზემოთ ჩამოთვლილი read-only მისამართები და არსებული მონაცემების შენარჩუნება.
4. GitHub-ში საჭირო კოდის revert მოამზადეთ ცალკე PR-ად. ამ გამოშვებაში მიგრაცია და
   მონაცემთა ცვლილება არ არის, ამიტომ DB rollback ოპერაცია ამ პროცედურის ნაწილი არ არის.
