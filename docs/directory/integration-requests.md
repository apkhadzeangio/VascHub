## Production Launch-ის შემდეგ

1. შეადარეთ დასრულებული main BASE_SHA-ს და შეათანხმეთ აუცილებელი საერთო ფაილები.
2. გაერთიანებული Payload კონფიგურაციიდან ხელახლა გაუშვით ტიპების გენერაცია.
3. თუ Events/Training-იც ცვლის lock relationship-ებს, გადაამოწმეთ საერთო მიგრაციების
   რიგი/snapshot და გააგენერირეთ შემდეგი snapshot გაერთიანებული სქემიდან. ძველი მიგრაციები არ შეცვალოთ.
4. გაერთიანებულ კოდზე გაიმეორეთ მიგრაცია და მიზნობრივი ტესტები იზოლირებულ PostgreSQL 16-ზე.
5. გლობალურ ნავიგაციაში „პროფესიული ქსელი“ დააკავშირეთ `/specialists`-ზე.
   ცნობარის შიდა ჩანართი უკვე გადადის `/centres`-ზე. Header/Footer ამ PR-ში უცვლელია.
6. რეალური პროფილების გადამოწმება და Production-ში შევსება ცალკე სარედაქციო სამუშაოა.

## MVP-ის საზღვრები

- ქალაქი/მიმართულება თავისუფალი ტექსტია; საჭიროა თანმიმდევრული მართლწერა.
- ძიება სახელის substring-ით მუშაობს; fuzzy search/ტრანსლიტერაცია არ შედის.
- B-tree სახელის substring ძიებას სრულად ვერ აჩქარებს; დიდი კატალოგის ოპტიმიზაცია
  რეალური მოცულობის მიხედვით უნდა შეფასდეს.
- distinct ფილტრები სრულად იკითხება; ცენტრების dropdown ყველა საჯარო სახელს/Slug-ს
  ტვირთავს. ძალიან დიდი ცნობარისთვის searchable selector შეიძლება ცალკე გახდეს საჭირო.
- Slug redirect და ცნობარის ცალკე sitemap ამ MVP-ში არ დამატებულა.
- native ანონიმური relationship query-ის შეზღუდვები აღწერილია README-ში.
- merge, deploy და Production QA არ შესრულებულა; საწყისად ცარიელი ცნობარი გამართულად მუშაობს.
