ქართული კლინიკური ბიბლიოთეკა არსებული VascHub-ის ფარგლებში. სამუშაო ბრენჩი:
`feat/clinical-library-v0.1`; საწყისი `main`: `8030f63` (გაერთიანებული PR #3).

## გვერდები და ინტეგრაცია

- `/library`: რეალური PostgreSQL ძიება, ხუთი ფილტრი, ტიპებისა და თემების სწრაფი
  ბმულები, შედეგების რაოდენობა, დახარისხება და გვერდებად დაყოფა.
- `/library/[slug]`: ქართული და ორიგინალური სათაური, სამეცნიერო მეტამონაცემები,
  ციტირება, წყარო, DOI/PubMed, გამოცემის სტატუსი და დაკავშირებული საჯარო რესურსები.
- `/library/[slug]/pdf`: თითოეულ მოთხოვნაზე უფლებების შემოწმება და PDF-ის stream.
- `/library-sitemap.xml`: მხოლოდ გამოქვეყნებული საჯარო რესურსები.

მთავარ ნავიგაციაში დაემატა ბიბლიოთეკა; CMS-ის ძველი `/#resources` ბმული
ახალ მისამართზე გადადის. მთავარი გვერდის ბიბლიოთეკის სექცია აჩვენებს სამ ბოლო
დამატებულ რესურსს. არსებული Posts-ის ბარათები, Featured Resources-ის არჩევანი,
სტატიების გამოქვეყნება და `/search` შენარჩუნებულია.

ინტერფეისი იყენებს არსებულ Header/Footer-ს, Noto Sans Georgian-ს, VascHub-ის
ფერებსა და shadcn/ui კომპონენტებს. აქვს ფორმის label-ები, 44px მოქმედებები,
ხილული keyboard focus, responsive grid, ცარიელი შედეგები, შეცდომის და ჩატვირთვის
მდგომარეობები. Loading boundary მხოლოდ `(catalog)` route group-შია, რათა
დეტალური გვერდის არარსებულმა/draft slug-მა რეალური HTTP 404 დააბრუნოს.

## ადმინისტრატორის სამუშაო პროცესი

1. შედით არსებულ `/admin`-ში და საჭიროებისას დაამატეთ კლასიფიკატორი.
2. შექმენით რესურსი: ქართული სათაური, რეზიუმე, ტიპი, მიმართულებები, ორგანიზაცია,
   ენა და გამოცემის წელი. ორიგინალური სათაური ჩაწერეთ ზუსტად წყაროდან.
3. გადაამოწმეთ გამომცემელი ან PubMed; შეავსეთ დადასტურებული DOI/PMID და ციტირება.
   თუ ზუსტი დღე უცნობია, `publicationDate` დატოვეთ ცარიელი — წელი თარიღად არ გამოიცნოთ.
4. მიუთითეთ ოფიციალური HTTPS წყარო და `lastReviewedAt`. ეს ველები აუცილებელია
   გამოქვეყნებისთვის. მათი არსებობა ავტომატურ სამეცნიერო peer review-ს არ ნიშნავს.
5. შეინახეთ Draft ან გამოაქვეყნეთ საჯაროდ. `visibility=internal` საჯარო API-დან,
   ძიებიდან, დაკავშირებული რესურსებიდან, sitemap-იდან და PDF route-იდან დამალულია.
6. ახალი გამოცემის დადასტურებისას შეავსეთ სტატუსი, მტკიცებულების ბმული და,
   თუ კატალოგშია, ახალი ჩანაწერის `supersededBy`. CMS-ის `updatedAt` არ არის
   კლინიკური დოკუმენტის განახლების თარიღი.

სტატუსი `not-assessed` მომხმარებელს პირდაპირ ატყობინებს, რომ მოგვიანებითი
განახლება არ არის შეფასებული. `updated` და `superseded` მტკიცებულების HTTPS
ბმულის გარეშე ვერ გამოქვეყნდება. სისტემა არც ერთ ჩანაწერს ავტომატურად არ
აცხადებს „უახლესად“.

## PDF, საავტორო უფლებები და საცავი

ნაგულისხმევია **External Resource**: მეტამონაცემები და ოფიციალური ბმული;
მესამე პირის PDF არ ჩამოიტვირთება, არ დაკოპირდება და არ პროქსირდება.

Hosted PDF-ისთვის აუცილებელია:

- `library-files`: `.pdf`, `application/pdf`, `%PDF-` signature, Payload-ის
  რეალური ტიპის შემოწმება და მაქსიმუმ **20 MiB** როგორც declared size-ით,
  ისე ბაიტების რეალური რაოდენობით; ფაილს ეძლევა შემთხვევითი UUID სახელი.
- `rightsConfirmed=true` და ფაილის `rightsNote`; ეს ინფორმაცია საჯაროდ არ იკითხება.
- რესურსზე `accessType=hosted`, `attachmentType=pdf`, დამტკიცებული `licenseStatus`
  (`open-license`, `permission-granted` ან `owned`) და არაცარიელი `rightsEvidence`.
  ადმინისტრაციული მტკიცებულება field-level ACL-ითაა დაცული.
- ქართული თარგმანის შემთხვევაში უნდა იყოს თარგმნისა და გავრცელების შესაბამისი
  უფლებებიც; მხოლოდ ონლაინ ხელმისაწვდომობა საკმარისი საფუძველი არ არის.

ფაილის `rightsConfirmed`-ის გაუქმება ან რესურსის გაუქვეყნება დაუყოვნებლივ წყვეტს
ჩამოტვირთვას. საჯარო download პასუხს აქვს `no-store`, `nosniff`, `noindex`, CSP
`sandbox` და `Content-Disposition: attachment`. stream-ს წინ უძღვის რეალური
ფაილის ზომის შემოწმება; ერთ მოთხოვნაზე სრული 20 MiB buffer არ იტვირთება.

Railway-ზე გამოიყენეთ **არსებული** `vaschub-media` volume, `/app/media-data` mount.
რეკომენდებული ზუსტი გზა: `LIBRARY_FILES_DIR=/app/media-data/library-private`.
თუ `LIBRARY_FILES_DIR` არ არის მითითებული და `MEDIA_DIR` `public/`-ის გარეთაა,
გამოიყენება მისი `library-private` ქვედირექტორია; სხვა შემთხვევაში ლოკალური
fallback არის `private/library-files`. `public/`-ში PDF დირექტორია აკრძალულია.

Media-ის ფაილის read grant ახლა მოითხოვს რეგისტრირებული Media ჩანაწერის შესაბამის
filename-ს. ეს ინარჩუნებს ჩვეულებრივ საჯარო მედიის მიღებას და კეტავს საერთო
volume-ში არსებული ბიბლიოთეკის ფაილების მიღებას `/api/media/file/...` გზით.
Compose-ის იგივე `media_data` volume ახლა `/app/media-data`-ზეა მიბმული; მისი
არსებული ფაილები root-ში რჩება. ახალი volume ან bucket არ დამატებულა.
სარეზერვო ასლში შეიტანეთ მთელი media volume და ბაზა ერთად.

არ არის დამატებული ანტივირუსი, PDF-ის აქტიური შიგთავსის სანიტიზაცია ან ჯამური
filesystem quota. 20 MiB ზღვარი თითო ფაილზეა; საერთო 500 MB volume-ის შევსება
ადმინისტრატორმა უნდა აკონტროლოს Railway-ში. v0.1-ის seed-ს ფაილები საერთოდ არ აქვს.

## ძიება და ფილტრები

URL-ის პარამეტრებია `q`, `topic`, `organization`, `type`, `year`, `language`,
`sort` (`added`, `year`, `title`) და `page`. ბმულები მათ ინარჩუნებს; ახალი ფილტრის
გამოყენება იწყება პირველი გვერდიდან. ერთი გვერდის მაქსიმუმია 12 ჩანაწერი,
ძიების ტექსტი 160 სიმბოლოა, page მაქსიმუმ 10,000.

ძიება ხდება ქართულ/ინგლისურ სათაურში, რეზიუმეში, ავტორებში, საკვანძო სიტყვებში,
DOI-ში, თემის დასახელებასა და ორგანიზაციის დასახელებაში/აბრევიატურაში.
ტექსტი NFC-ით ნორმალიზდება; query lower-case-დება (მათ შორის მთავრული ქართული).
Payload-ის `like` გამოიყენება PostgreSQL-ის case-insensitive ძიებით; SQL ხელით
არ აიწყობა. ქართული მორფოლოგიური ან სრული PDF ტექსტის ძიება არ ხორციელდება.
B-tree ინდექსები ფილტრაციას ეხმარება; substring ძიება დიდი კორპუსისთვის ცალკე
ოპტიმიზაციას მოითხოვს.

ყველა frontend მოთხოვნა სრულდება სტუმრის უფლებებით (`overrideAccess:false`,
`draft:false`) სერვერის შიდა Local API-შიც. ავტორიზებული ადმინისტრატორიც კი
საჯარო გვერდზე draft-ს ვერ ხედავს. წერითი ოპერაციები და version history მხოლოდ
არსებული CMS-ის ავტორიზებული თანამშრომლებისთვისაა დაშვებული.

## უსაფრთხო იმპორტი

```sh
pnpm payload run scripts/seed-library.ts
```

გამოქვეყნებისთვის, შესაბამის გარემოში:

```sh
LIBRARY_SEED_PUBLISH=1 pnpm payload run scripts/seed-library.ts
```

მეორე რეჟიმი უკვე არსებულ მონახაზებსაც არ აქვეყნებს. იმპორტი არსებულ მასალას
პოულობს importKey-ით, slug-ით, DOI-ით ან PMID-ით და მთლიანად გამოტოვებს მას.
არ ცვლის სათაურს, სტატუსს, რედაქტორის ცვლილებებს ან სხვა მონაცემებს; არაფერს
შლის. ტაქსონომიებიც იქმნება მხოლოდ არარსებული slug-ისთვის. მონაცემების წყარო
ვერსიაკონტროლირებულია; runtime-ზე დაუდასტურებელი ქსელური მონაცემები არ ქვეყნდება.
ერთ გარემოზე ერთდროულად გაუშვით ერთი იმპორტი; unique keys დამატებით კეტავს
იგივე სტაბილური ჩანაწერის დუბლირებას.

ლოკალური Library prototype-ის მიგრაცია საბოლოო სქემით ჩანაცვლდა; მისი ცალკე
გამოყენება საჭირო არ არის. ეს PR განკუთვნილია production-ის `8030f63` სქემიდან
განახლებისთვის. ძველ ლოკალურ prototype ბაზაზე პირდაპირ არ გაუშვათ.

UP ამატებს მხოლოდ ახალ ცხრილებს, enum-ებს, ინდექსებსა და Payload lock-ის

DOWN შლის ბიბლიოთეკის ცხრილებსა და კონტენტს; მხოლოდ იზოლირებულ test ბაზაზე

Railway-ზე შემოწმებული start command უკვე არის:
`sh -c 'pnpm db:migrate && exec pnpm start --hostname 0.0.0.0'`.
ფუნქციის განთავსებამდე შეამოწმეთ ფაილის ზუსტი გზა და volume-ის write უფლებები;

მნიშვნელობის/რეალური PDF-ის restart-ზე შენარჩუნების დადასტურება არ ივარაუდება.
Production DB-ზე არც მიგრაცია და არც seed ამ სამუშაოში არ შესრულებულა.

Railway-ში არსებული ორი 500 MB volume, ორი service და წინასწარ არსებული
`vaschub-documents` bucket შენარჩუნებულია; bucket ამ ფუნქციაში არ გამოიყენება.
ახალი პროექტი, ბაზა, paid search/storage, R2 ან გეგმის ცვლილება არ შექმნილა.

**0.7113 GB**), CPU **0.000021** მიმდინარე / **0.01008** საშუალო, disk metric
**0.0322 GB**. ეს baseline-ია და არ წარმოადგენს ჯერ გაუშვებელი ახალი ფუნქციის
გაზომილ გავლენას. კორპუსი მხოლოდ მცირე მეტამონაცემებს ამატებს; PDF-ების საერთო
ადგილი ცალკე კონტროლს საჭიროებს.
