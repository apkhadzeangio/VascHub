მიგრაციისა და საერთო ფაილების შეცვლის გარეშე**.

გადაბაზირებულია განახლებულ `main`-ზე `8fc2607780899b3c3530cd6cd10232be23b2fc21` (PR #8 შერწყმულია).

## რა მუშაობს

- ტიპის ფილტრი: **ღონისძიებები** / **პროფესიული განვითარება** (+ „ყველა“, თითოეულზე რაოდენობით).
- ტექსტური ძიება (სათაური, აღწერა, ადგილი; ყველა სიტყვა უნდა დაემთხვეს).
- გვერდებად დაყოფა (12 ჩანაწერი), შედეგების რაოდენობა, ცარიელი / loading / error მდგომარეობა.
- მდგომარეობა მისამართშია: `/events?type=events&q=…&when=upcoming&page=2`. უცნობი ან დაზიანებული
  პარამეტრი უბრალოდ უგულებელყოფილია; გასული გვერდის ნომერი უახლოეს რეალურ გვერდზე გადადის.
- ბარათი: სათაური, მოკლე აღწერა, ტიპი, თარიღი/ადგილი (მხოლოდ თუ წყაროშია) და ერთადერთი ბმული
  (სათაური, რომელიც მთელ ბარათზეა გაშლილი — ერთი Tab-გაჩერება).

## მონაცემთა წყაროები (მხოლოდ რეალური ველები)

| წყარო | გამოყენებული ველები | შენიშვნა |
| --- | --- | --- |
| `posts` (გამოქვეყნებული) | `title`, `slug`, `meta.description`, `categories` | კატეგორია მოიძებნება **slug-ით**: `international-events` → ტიპი „ღონისძიებები“; `professional-development` → „პროფესიული განვითარება“. დეტალური გვერდი — არსებული `/posts/[slug]`. |
| `pages` › `home` › `homepage.events` | `title`, `date`, `location`, `url` | ერთადერთი წყარო, სადაც სტრუქტურირებული თარიღი და ადგილი არსებობს. |

**არ გამოიყენება:** `publishedAt` / `updatedAt` ღონისძიების თარიღად; თარიღი სათაურიდან ან
Rich Text-იდან; არქივის JSON; Clinical Library-ის მონაცემები. არ არსებობს და არც გამოგონილია:
`eventDate`, `deadline`, `registrationStatus` ან სხვა ველი.

## წესები

**თარიღები (Asia/Tbilisi).** შედარება ხდება თბილისის კალენდარული დღით (`src/Events/dates.ts`).
დღევანდელი დღის ღონისძიება „მომავალია“; წინა თბილისური დღე — „ჩატარებული“.
ჩანაწერი **თარიღის გარეშე** ან არავალიდური თარიღით (`1900–2100`-ის გარეთ, დაუშვებელი ფორმატი)
→ „თარიღი დასაზუსტებელია“, **არასდროს** „მომავალი“; გვერდი არ ითიშება.
დალაგება: მომავალი (უახლოესი პირველი) → თარიღის გარეშე (ანბანით) → ჩატარებული (უახლესი პირველი).

**თარიღის ფილტრი** (`when=upcoming|past|undated`) ჩანს მხოლოდ მაშინ, როცა მონაცემებში ერთი
ვალიდური სტრუქტურირებული თარიღი მაინც არსებობს.

**განაცხადი / რეგისტრაცია.** გვერდი არ აცხადებს განაცხადს „ღიად“ და რეგისტრაციას „აქტიურად“ —
ამისთვის წყაროში ველი არ არსებობს.

**პროფესიული განვითარება** არ არის „ტრენინგის“ სინონიმი: მასში fellowship, observership,
გრანტიც შეიძლება შედიოდეს, ამიტომ ბარათზე ზოგადი ეტიკეტი „პროფესიული განვითარება“ წერია.

**დუბლიკატები.** მთავარი გვერდის მოკლე ცნობა, რომლის `url` ერთსა და იმავე Post-ზე მიდის, არ
ქმნის მეორე ბარათს — ის ამდიდრებს Post-ის ბარათს თარიღითა და ადგილით და Post-ს „ღონისძიებების“
ტიპსაც ამატებს. ერთი და იგივე გარე ბმული (ბოლო `/`-ისა და დომენის რეგისტრის სხვაობით) ერთხელ ჩანს.

**წვდომა.** ყველა წაკითხვა Local API-ით ხდება `overrideAccess: false`, `draft: false`,
`user`-ის გარეშე და აშკარა `_status = published` პირობით. კოდი `draftMode()`-ს არ კითხულობს, ამიტომ
ადმინისტრატორის სესია ან Preview cookie Draft-ს საჯარო სიაში ვერ გამოაჩენს (e2e-ით შემოწმებულია).
მთავარი გვერდისთვის წაიკითხება მხოლოდ **გამოქვეყნებული ვერსია**.

**ბმულები.** გამოიყენება არსებული `publicHref` (მხოლოდ ლოკალური გზა ან `http(s)`, პაროლისა და
`javascript:`-ის გარეშე). შიდა ბმული დაიშვება მხოლოდ `/posts/<slug>` ან `/library/<slug>` ფორმით და
მხოლოდ მაშინ, თუ სამიზნე ახლა საჯაროდ გამოქვეყნებულია; წინააღმდეგ შემთხვევაში ბარათი საერთოდ არ
იქმნება (არც გატეხილი, არც Draft-ზე მიმავალი). სხვა ლოკალური გზები უარყოფილია, რადგან მათი
ხელმისაწვდომობის შემოწმება შეუძლებელია. გარე ბმული იხსნება ახალ ფანჯარაში
`target="_blank" rel="noopener noreferrer"`-ით და ეკრანის წამკითხველს ამის შესახებ ეუბნება.

## ცნობილი შეზღუდვები (MVP)

1. **Posts-ს ღონისძიების თარიღი/ადგილი/ბმული/ვადა არ აქვს**, ამიტომ Post-ზე დაფუძნებული ბარათები
   ყოველთვის „თარიღი დასაზუსტებელია“-ა, თუ მათზე მთავარი გვერდის ცნობა არ მიუთითებს.
   სტრუქტურირებული თარიღი მხოლოდ მთავარი გვერდის ცნობებშია, და იქ მაქსიმუმ **2 ჩანაწერია**
   (`maxRows: 2`).
2. ქვეტიპები (ტრენინგი / fellowship / observership / გრანტი) CMS-ში არ არსებობს, ამიტომ
   ცალკე ფილტრად არ არის გამოყვანილი.
3. ძიება, დალაგება და გვერდებად დაყოფა მეხსიერებაშია, რადგან ორი წყარო ერთიანდება.
   ერთ მოთხოვნაზე იკითხება მაქსიმუმ `MAX_POSTS = 1000` Post (`src/Events/queries.ts`); ამაზე მეტზე
   საჭიროა DB-დონის ძიება (იხ. `integration-requests.md`, §5).
4. კატეგორიების slug-ები `international-events` და `professional-development` **ტესტურ ბაზაში**
   შემოწმდა; Production CMS-ზე წვდომა არ მქონია, ამიტომ მათი იქ არსებობა **დადასტურებული არ არის**.
   თუ რომელიმე არ არსებობს, შესაბამისი Post-ები უბრალოდ არ გამოჩნდება (პატიოსანი ცარიელი მდგომარეობა).
5. `loading.tsx` (როგორც არსებულ `/library`-ზე) Next.js-ის streaming-ს ეყრდნობილია: JavaScript-ის
   გარეშე გვერდი „იტვირთება…“ მდგომარეობაში რჩება. ამიტომ „JS-ის გარეშე მუშაობას“ არ ვაცხადებთ.
6. Production-ის ექვსივე არსებული Post მონახაზია — გამოქვეყნებამდე `/events` ცარიელ მდგომარეობას
   აჩვენებს. გვერდის შესავსებად არაფერი გამოქვეყნებულა.
